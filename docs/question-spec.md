## 0. 조사 결과 요약 (표본 24문항 문형 분포)

| 문형 | 표본 수 | 특징 |
|---|---|---|
| ① 소문항형 | 18 (75%) | 리드문 + `가.~라.` 또는 `1)~3)` 마커. 소문항 2~4개가 지배적 |
| ② 인라인 나열/복동사형 | 3 (13%) | 마커 없이 본문에 "A, B 및 C에 대하여 설명하시오" 또는 "~하고 ~한 후 ~를 제시하시오" |
| ③ 단순형 | 3 (12%) | 단일 요구 (+괄호로 측면·개수 지정) |

핵심 관찰 (설계에 반영):
- **시나리오 지문은 독립 문형이 아니다** — "B기관은 ~하려고 한다"류 리드는 ①②③ 어디에나
  얹히는 **수식 속성**이다(표본 6건). 별도 문형이 아니라 `scenario` 필드로 처리한다.
- 소문항이 **요구(동사구)**인 경우와 **대상(명사) 나열**인 경우가 갈린다(표본 #6 메모리
  4영역, #17 마이닝 3기법 — 동사는 리드에 1회만 등장). 파서가 이 둘을 구분해야 한다.
- **괄호 지정**이 채점 포인트다: "(범위, 책임/목표, 주요 산출물 측면)"(#4), "(정의,
  주요투입물, 작성방법 등)"(#16), "(2개 이상)"(#14), "4가지 제시하고"(#7).
  방법론: "괄호 안의 요구 사항 글자 내용까지 꼼꼼하게" [2교시 6/71].
- 채점은 요구 단위다: "물어본 것 3개인 경우 각각 5점씩" [2교시 70/71], 목차는 "물어본
  지문 text 그대로" [2교시 55~56/71], 누락 = 감점.

## 1. 목표

2교시 문항을 요구사항 리스트로 파싱(무LLM 우선)하고, 요구 순서대로 Ⅱ~Ⅳ 단락에
토픽 부품을 배치하며, 서론 로드맵이 "물어본 것"을 그리게 한다. 라이브러리 적중 경로의
LLM 예산(0~2콜)·3초 목표는 유지한다.

## 2. 요구사항

### 2-1. 문항 파서 (`api/_question.py` 신설, 무LLM 규칙 우선)

출력 스키마 (조립기·집필·검증이 공유하는 계약):

```json
{
  "form": "sub | inline | simple",
  "scenario": "리드 지문(있으면, 원문 그대로)",
  "requirements": [
    {
      "label": "가",                          // 마커 (inline/simple은 자동 부여 R1, R2…)
      "text": "오픈소스 DBMS 전환 시 단계별 마이그레이션 절차",   // 원문 보존 — 목차 스탬프용
      "verb": "explain",                      // explain|compare|propose|define|reason|apply
      "objects": ["마이그레이션 절차"],         // 요구 대상 명사구(1~3개)
      "slots": ["procedure"],                 // 2-2 매핑 결과 (파서가 1차 결정)
      "sub_points": ["범위", "책임/목표", "주요 산출물"],  // 괄호·"N가지" 지정 (없으면 [])
      "count": 4                              // 개수 지정 (없으면 0)
    }
  ],
  "parse": "rule | llm | fallback"            // 어떤 경로로 파싱됐는지 (reply에 노출)
}
```

파싱 규칙 (순서대로 적용):

1. **마커 분리**: 정규식 `^[가나다라마바]\.` / `^\d[).]` / `^[①-⑩]` (행 시작). 인라인
   병기("가. ~ 나. ~"가 한 줄)도 lookahead `(?=[가-바]\.\s)`로 분리. 마커 검출 시 `form=sub`,
   마커 이전 텍스트는 리드 — 문장형이면 `scenario`로 보존.
2. **대상 나열형 판별**: 소문항 전부가 종결어미 없는 명사구(20자 이하)이면 대상 나열형.
   리드의 동사("각 ~에 대하여 설명하시오")를 각 대상에 복제해 요구 N개를 만든다.
   (표본 #6, #17, #19 — 이걸 놓치면 "가. 코드"가 요구 문장으로 오독됨)
3. **복동사 분해**: 소문항/본문의 연결어미 패턴만 보수적으로 분해 —
   `…하고, …` / `…한 후 …` / `…를 제시하고 각 … 이유` (표본 #7, #13, 합성 #20류).
   한 요구에서 최대 2개까지만 분해(과분해 방지).
4. **인라인 나열**: 마커가 없고 `…에 대하여/…을(를)` 앞에 콤마·"및" 나열구가 있으면
   나열 항목을 요구로 분리 (`form=inline`, 표본 #20 "필요성, 주요기준, 문제점 및
   개선방향"). 나열 항목이 명사구 판정(2 규칙)을 통과할 때만 분리, 아니면 simple.
5. **괄호·개수**: 각 요구 텍스트의 `(…)` 내 콤마 나열 → `sub_points`(표 헤더·h3 반영),
   `N가지`/`N개 이상` → `count`.
6. **동사·슬롯 태깅**: 2-2의 사전으로 verb/slots 결정.
7. **LLM 폴백 (1콜)**: 요구 0건, 마커·어미 불일치 잔여 텍스트가 전체의 30% 초과, 또는
   요구 6개 초과(과분해 의심)일 때만. 프롬프트는 위 JSON 스키마를 그대로 요구하고,
   **원문에 없는 요구 생성 금지**(요구 text는 원문 부분 문자열이어야 함 — 서버가 검증,
   위반 시 규칙 파싱 결과로 폴백). 키 없으면 `form=simple` 1요구로 처리(`parse=fallback`).
8. 1교시형(용어형 10점)은 파서를 거치되 요구 1~2개의 simple로 수렴 — 기존 경로 무변경.

### 2-2. 요구 → 단락·부품 슬롯 매핑

**단락 배치 규칙** (방법론 [2교시 8/71] "Ⅱ=첫 요구, Ⅲ=둘째, 물어본 것이 많으면 Ⅳ단락 동일"):

| 요구 수 N | 단락 구성 |
|---|---|
| 0~1 | Ⅰ 서론 / Ⅱ 기본구성(구성도+구성요소 [2교시 54/71]) / Ⅲ 요구(또는 심화) / Ⅳ 결론 — 현행 유지 |
| 2 | Ⅰ / Ⅱ=R1 / Ⅲ=R2 / Ⅳ 결론(활용·기대효과) |
| 3 | Ⅰ / Ⅱ=R1 / Ⅲ=R2 / Ⅳ=R3 + 결론 2줄 |
| 4~5 | Ⅰ / Ⅱ=R1 … Ⅴ(~Ⅵ)=R4(R5) + 마지막 단락 말미 결론 2줄 — 병렬식 [2교시 49/71] |

- 단락 수는 가변(최대 Ⅵ). `answer-template-spec.md` §5의 4단락 표는 "N=2 기준"임을
  명시 개정한다(다인 협의 — 줄 그리드·프래그먼트 계약은 무변경, h2 개수만 가변).
- **요구 순서 = 단락 순서** (순서 재배열 금지 — "순서 바꾸어도 되나요? 10%" [2교시 56/71],
  안전하게 원순서 고정). 단락 제목은 요구 `text` 원문 기반으로 스탬프(지문 그대로 목차).
- `sub_points`가 있으면 해당 단락 안에서 가.나. 하부 목차 또는 표의 구분열로 반영.
- `count` 지정 시 표 행 수를 count 이상으로 (부품 행이 부족하면 부족분 LLM/플레이스홀더).

**동사·트리거 → 부품 슬롯 매핑** (대상 명사구의 트리거가 동사보다 우선):

| 트리거(대상 명사 우선) | verb | 1순위 부품 | 대체 순서 | 렌더 |
|---|---|---|---|---|
| 개념·정의·개요 | define/explain | definition_long | definition | h3+def 2줄 |
| 배경·필요성·중요성·이유 | reason | background | definition_long | t2 표 또는 def |
| 구성요소·기술요소·기능·유형·종류 | explain | components | features | t3 9줄 상세표 |
| 구성도·아키텍처·개념도·메커니즘 | explain | diagram_html | (LLM/생략) | diagram 6줄 |
| 절차·과정·단계·프로세스 | explain | **procedure (신규 부품)** | components | t3 절차표(step 열) |
| 비교·차이점·vs | compare | comparisons | 자동 대비표(_auto_compare_axes) | tcmp |
| 방안·개선방향·대응방안·활용·기대효과·전망 | propose | usage | exam_points | t2 표 |
| 특징·장단점·한계 | explain | features | components | t2/t3 |
| 사례·경험 적용 | apply | (부품 없음) | exam_points | LLM 집필 대상 (2-4) |

**스키마 확장** (`api/_library/schema.md` v1.1, library-spec 2-1 개정):
선택 부품 `procedure: [{"step": 1, "name": "평가", "desc": "…"}]` 추가.
표본 24문 중 8문이 절차·단계를 물었다 — 기존 부품으로는 대체 렌더가 어색해 신설이 타당.
build_index.py 검증 규칙에 procedure 스키마 추가. 기존 풀부품 20건 중 절차성 토픽
(ISP·ISMS·재공학·DRS 등)에 procedure를 보강하는 배치 작업은 별도 마일스톤.

### 2-3. 로드맵 서론 동적화 (Type IV [2교시 42~43/71])

현행: 고정 부품(diagram_html)을 서론에 배치. 변경: **서론 로드맵은 요구사항으로 그린다** —
"물어본 가, 나, 다 항목을 Ⅱ, Ⅲ, Ⅳ 단락 기술할 내용을 하나의 도식화/서론 그림으로" [2교시 42/71].

- 조립기가 `.diagram.d7`을 **생성**한다: 요구별 `d-box` (라벨 = 단락 라벨 요약, 12자 이내
  명사구 절삭) + `d-arrow` 순서 연결 + 토픽 `d-hub`(복합이면 대표 토픽) + 하단 정의 2줄
  (`definition`, 간글 형태 [2교시 43/71] "정의 2줄 + 필요성 2줄").
- **박스 텍스트는 Ⅱ~단락 h2 제목의 요약과 일치해야 한다** (세아 검증 항목: 로드맵
  박스 수 == 요구 수, 각 박스 텍스트가 해당 h2 제목의 부분 문자열).
- 서론 타입 선택 규칙(간소): 요구 2개 이상 → Type IV(기본) / 요구 0~1 + 정의성 토픽 →
  Type I(현행 _slot_intro_p2 유지) / 보안 도메인(category에 보안·SEC) → Type III 리드문
  제목만 차용. 타입 V·VI 렌더 분화는 이번 범위 밖(제외 범위).

### 2-4. 부품 부족 시 처리 (llm_calls 예산 불변: 적중 경로 0~2콜)

1. 요구 슬롯의 1순위 부품 부재 → 2-2 대체 순서로 강등 시도 (경고 없이).
2. 대체까지 전멸 →
   - **키 있음**: 부족 요구들을 **한 번에 모아 LLM 1콜**로 소단락 집필. §7 프래그먼트
     계약 준수(허용 태그·클래스만, 표는 r2 규칙), 시스템 프롬프트에 요구 text·sub_points·
     토픽 keywords 주입. 출력이 계약 위반이면(린트) 플레이스홀더로 강등.
   - **키 없음**: 플레이스홀더 표(요구 text + "라이브러리 미등록 부품" 1행) + reply 경고.
3. 콜 예산 합산 규칙: 파서 LLM 폴백(≤1) + 부족 슬롯 집필(≤1) + 기존 모호 매칭(≤1) 중
   **총 2콜 상한** — 초과분은 키가 있어도 무LLM 경로(플레이스홀더/규칙 파싱)로 강등.
   reply의 `llm_calls`에 그대로 반영.

### 2-5. 분량 재배분 (`_volume` 개정)

총량 3~3.5매(66~77줄, 22줄/쪽)는 불변 [2교시 5~6/71]. 고정비: Ⅰ 서론 10~12줄,
결론 블록 5~8줄(단독 Ⅳ일 때; R3+에 합류 시 2줄), "끝"+암기 박스 4줄, 단락 간 gap N줄.
잔여 본문 줄을 요구 수로 배분:

| N | 요구당 목표 | 환산 |
|---|---|---|
| 1~2 | 20~22줄 | 각 ~1쪽 — "물어본 것은 2/3~1페이지" [2교시 55~56/71] |
| 3 | 14~15줄 | 각 ~0.7쪽 |
| 4~5 | 10~11줄 | 각 ~0.5쪽, 총량이 3.5매 초과 시 3매 하한 우선 |

- 요구당 최소 7줄(h2 1 + 표 헤더1+행4 + 마무리 1) 보장. 배분 결과에 따라 부품 렌더
  밀도를 조절: 넉넉하면 9줄 상세표+간글, 빡빡하면 헤더1+r2행3의 7줄 압축표.
- 페이지 계측·분할은 현행 `_layout` v2 그대로 (템플릿 스펙 §8).

  가. ISP의 정의 및 목적 나. ISP 수행방법론 체계와 절차 다. ISP, ISMP 비교" → MG-047/MG-048
